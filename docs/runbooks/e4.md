## Procesamiento y diagnóstico

El reporte físico `DELIVERED` crea un aviso por padre activo/vinculado en la misma
transacción. Escaneo, confirmación digital, incidencia sin entrega y
`NOT_DELIVERED` no generan aviso de retiro. El envío espera recibo del reporte con
hash, versión y retención vigentes. Se revalida destinatario antes de reclamar;
una baja/vínculo retirado suspende el pendiente.

El mensaje externo es genérico y solo incorpora un UUID lógico. Una respuesta
perdida del proveedor puede producir un duplicado externo; conserva el mismo
aviso lógico y nunca crea otra salida. Las llamadas de red no mantienen locks SQL.
Leases de 60 s, lotes seriales de hasta tres. Reintentos tras fallo: 30 s, 2 min,
5 min y 15 min; se respeta Retry-After más largo. Después del quinto intento
permanece pendiente de revisión y se alerta; no se inventa recepción.

| Estado | Significado |
| --- | --- |
| PENDING | En cola; puede esperar protección o reintento. |
| PENDING_DEVICE | Sin dispositivo activo; pendiente y escalado después de 15 min. |
| PENDING_REVIEW | Reintentos agotados o incertidumbre prolongada; requiere operación técnica. |
| PROVIDER_ACCEPTED | Expo aceptó un ticket; no acredita recepción/lectura. |
| PROVIDER_RECEIPT | Expo informó traspaso a FCM/APNs; no acredita recepción/lectura. |
| SUPPRESSED | Cuenta o vínculo ya no habilitados. |

Expo no publica un callback de entrega usado por esta aplicación. Se consultan
sus recibos por HTTPS autenticado, asociados a tickets persistidos. Un endpoint
público falso devuelve 404; credenciales runtime/lectores no pueden fabricar
estados del notificador. Consulta inicial a los 15 min según recomendación Expo;
recibo ausente alerta y se consulta cada minuto hasta el límite de 23 h, sin
reenviar automáticamente un aviso cuyo ticket ya fue aceptado.

Solo el proceso notificador recibe `PGUSER=retiro_notifier`/su contraseña o
`NOTIFICATION_DATABASE_URL`, `EXPO_PUSH_ACCESS_TOKEN` y
`EXPO_PUSH_ALLOWED_TOKEN_HASHES`. En cloud exige SQL `verify-full`; no recibe
Django secret, migrador/importer, credencial del archivador ni permisos KMS/S3.

```bash
python apps/backend/manage.py runworker --notifications --check
python apps/backend/manage.py runworker --notifications --once
python -m notification_worker.runner --max-runtime-seconds 10800
```

El runner necesita `PYTHONPATH=apps/backend` fuera de `/app`. Diagnóstico JSON sin
PII: pendientes, edad, escalados, aceptados/recibos y p95 hasta la primera
aceptación del proveedor. La alarma de CloudWatch requiere prueba efectiva del
canal técnico. La falta de métricas no acredita que el proceso funcione.

## Operaciones técnicas restringidas

Usar `IMPORT_DATABASE_URL` con identidad `retiro_importer`, TLS verificado en
cloud, motivo, aprobación escolar y operador reales. No inyectar esta credencial
en API/workers. Archivos privados de hasta 8 KB en directorio protegido; los
siguientes ejemplos son únicamente sintéticos. El commit no acredita archivo:
verificar después el evento con el archivador/lector externo.

Obtener hashes para la allowlist, sin exportar tokens:

```json
{"account_id":"UUID_PADRE_SINTETICO","id":"UUID_SOLICITUD","operator":"operador-verificado","approval":"aprobacion-del-ensayo","reason":"Incorporar dispositivo del equipo"}
```

```bash
python apps/backend/manage.py notification_ops device-hashes --file ARCHIVO_PRIVADO.json
```

Cada consulta añade auditoría propia. Guardar los hashes emitidos en el secreto
privado; no copiar el resultado al repositorio. Reemplazar la allowlist no reinicia
avisos ni cuentas. Actualizar/recrear el worker para inyectar el secreto vigente.

Reintentar el mismo aviso agotado después de resolver el proveedor:

```json
{"notification_id":"UUID_AVISO","id":"UUID_COMANDO","operator":"operador-verificado","approval":"aprobacion-verificada","reason":"Proveedor recuperado"}
```

```bash
python apps/backend/manage.py notification_ops retry --file ARCHIVO_PRIVADO.json
```

Conserva intentos/eventos previos y el UUID lógico; abre otro ciclo acotado. Replay
idéntico conserva el resultado; misma clave con contenido distinto falla. No
aplica a avisos ya aceptados, a padres deshabilitados ni a salidas.

Corrección histórica, sin editar el reporte ni conceder otra entrega:

```json
{"operation_id":"UUID_OPERACION","id":"UUID_COMANDO","operator":"operador-verificado","approval":"aprobacion-escolar","reason":"Hecho contrastado con la escuela","outcome":"UNRESOLVED"}
```

```bash
python apps/backend/manage.py pickup_correction --file ARCHIVO_PRIVADO.json
```

Resultados permitidos: DELIVERED, NOT_DELIVERED y UNRESOLVED. Exige reporte o
incidencia histórica. Añade `PICKUP_CORRECTION` relacionado con el reporte/decisión
o corrección anterior; los bytes originales, episodio y QR consumido se conservan.
No envía un nuevo aviso de retiro por interpretar una corrección.

## Consultas y ensayo integrado pendiente

`GET /v1/me/pickups`: móvil PADRE, principal o secundario habilitado, familia propia.
`GET /v1/school/pickup-records`: ADMIN_ESCUELA web, lector SQL separado; `/portal/`
comparte consulta. Filtros `from`/`to` (fecha local de sede), `student`, `limit`
1–100 y `before` por secuencia. Sin escritura ni exportación masiva; consultas
auditadas. Hasta 25 correcciones recientes por fila y contador total, conservando
el hecho original. Avisos del padre corresponden únicamente a su propia cuenta.
ADMIN_SISTEMA conserva accesos escolares, sin datos de menores ni salidas.

Para cerrar E4 en staging: cuatro roles/escuelas/familias cruzadas; portal/login
protegido; reporte oportuno/tardío/no entrega; replays/concurrencia/respuesta
perdida; ausencia/fallo de archivo; fallo/recuperación Expo y reintentos; recibo
falso/ajeno/repetido; corrección/reconciliación privada; alarma y p95 medidos.
Verificar la secuencia final con E1Verifier sin SQL/Sign/Put. Vincular resultados
al mismo SHA/digest/APK. La suite local y una confirmación de configuración en
consola no sustituyen este gate ni el ensayo físico E5.
