# E1 — identidad y evidencia sintéticas

Procedimientos de comisión, ensayo y diagnóstico. Estado, aceptación y límites
vigentes en [PLAN.md](../../PLAN.md#e1--identidad-aislamiento-y-base-de-evidencia).
Contrato funcional en [requisitos](../../Requerimientos_retiro_seguro_estudiantes.md);
parámetros del destino en [staging.json](../../infra/environments/staging.json).
Usar exclusivamente datos sintéticos en estas operaciones.

## Desarrollo y comprobación

Con `.env` preparado según el [README](../../README.md), `make install db check`
instala locks, actualiza roles locales idempotentes, migra con identidad separada
y ejecuta suites con PostgreSQL real. `make db` no borra volúmenes.
`infra/local/e1-roles.sql` es solo local; no aplicarlo en AWS.
`.env.example` mantiene `E1_IDENTITY_ENABLED=false`.

Las pruebas usan roles SQL runtime/importer/lector/archiver/notifier reales.
El migrador solo hace DDL e inyecta reloj/recibos en pruebas identificadas como
simuladas. OIDC local usa firmas RSA reales con proveedor simulado; el archivo
local simula S3/KMS. Estas pruebas no sustituyen ensayos con servicios AWS.

## Comisión AWS con operador

Revisar el commit y `infra/aws/e1-staging.yaml` desde un checkout limpio en
CloudShell, con AWS CLI/Python 3 y sesión de operador de la cuenta del proyecto:

```bash
python3 -m scripts.commission_e1 --web-origin https://ORIGEN_STAGING_VERIFICADO
```

Este comando corresponde a la comisión inicial. Obtener el origen del reporte
de despliegue del destino; `base_url` es una pista que puede quedar retirada.
Para recuperar una instalación existente tras recrear Express, no repetir esta
comisión: usar el bootstrap stateless y sincronizar solo el callback según
[deployment](deployment.md#origen-express-y-callback-existente). Los ensayos y el
APK reciben el origen verificado del candidato. Presupuesto, preflight y base: [AWS](../../infra/aws/README.md).

El comando verifica cuenta, operador, presupuesto CUSTOM, gasto y crédito vigente.
Reserva cinco USD para la comisión y 27 USD para base retenida como barrera
conservadora, sin sustituir el cálculo del inventario completo. Abre una ventana
RDS acotada y ejecuta bootstrap privado de roles con imagen existente por digest.
Los secretos pasan de Secrets Manager a ECS, sin devolver valores a CloudShell.
No crea usuarios IdP, estudiantes, invitaciones ni avisos. Su reporte
`work/e1-commission.json` conserva `e1_accepted=false`: comisionar no es aceptar.

El stack configura Cognito Essentials/Managed Login v2 con TOTP obligatorio;
la interfaz clásica no soporta `prompt=login`. El adaptador contrasta pool, MFA,
dominio v2 y cliente antes de aceptar tokens. No ampliar automáticamente el plan
si AWS rechaza ese nivel. Referencia:
[endpoint de autorización Cognito](https://docs.aws.amazon.com/cognito/latest/developerguide/authorization-endpoint.html).

El archivo usa bucket privado Object Lock COMPLIANCE de siete días, claves KMS
distintas, secretos y permisos separados. Esa retención solo sirve para ensayo;
no define conservación productiva. Recursos, claves y secretos quedan retenidos.
No borrarlos para reiniciar ensayos o ahorrar; no entregar permisos de operador
a la aplicación. Inspeccionar fallos privadamente en CloudFormation/CloudWatch.

## Procesos, permisos y verificación

| Proceso | Identidad y configuración |
| --- | --- |
| API/web | `retiro_runtime`; lector de accesos `retiro_system_read` con DSN separado y sin SELECT sobre menores/eventos completos. Sesión Django en servidor, cookies protegidas y CSRF. |
| Archivo | `retiro_archiver`; `ARCHIVE_DATABASE_URL` o PGUSER/PGPASSWORD propios, APP_ENV=staging, AWS_REGION, ARCHIVE_BUCKET, ARCHIVE_KMS_KEY_ARN, MANIFEST_KMS_KEY_ARN y ARCHIVE_RETENTION_DAYS=7. Sin credenciales web/migrador. |
| Verificador | Lectura/Decrypt/Verify independiente; sin SQL, Sign, PutObject ni secretos de negocio. OIDC GitHub/main exacto mediante `scripts/aws_oidc.py --role E1Verifier -- ...`. |
| Importación/migración | Tareas privadas; nunca inyectar sus credenciales en API/móvil. Las operaciones productivas de bulk/activación son E2. |

Archivo cloud con vida máxima de tres horas:

```bash
python -m archive_worker.runner --max-runtime-seconds 10800
```

Diagnóstico con la configuración y credenciales del proceso correspondiente:

```bash
python apps/backend/manage.py runworker --archive --check
python apps/backend/manage.py runworker --archive --once
python apps/backend/manage.py verify_archive --minimum-sequence ULTIMO_HIGH_WATER_EXTERNO
```

El mínimo es el último high-water externo confiable custodiado fuera de SQL,
no un valor de la BD investigada. Checkpoints/manifiestos referencian versión y
hash exactos. El formato canónico es `pg-jsonb-utf8-v1`; conservar bytes originales.
Firma KMS RSA-3072 PSS SHA-256. Ante discrepancia, suspender acceso afectado y
preservar evidencia; no recalcular hashes SQL para aprobar el verificador. La
rotación/recuperación debe conservar claves y versiones previas y ensayarse realmente.

## Fixtures privados de aceptación

Con stack y migraciones del candidato aplicados, desde el checkout limpio en
CloudShell:

```bash
python3 -m pip install --target work/e1-sdk --require-hashes -r infra/aws/e1-ops.txt
PYTHONPATH=work/e1-sdk python3 -m scripts.provision_e1_fixtures --synthetic-only
```

El SDK operativo fijado no modifica Python del sistema. La provisión prepara
13 cuentas individuales con TOTP y dos escuelas con dos familias cada una.
No envía mensajes. Contraseñas/semillas permanecen en AcceptanceFixtures;
API/worker no pueden leerlo. Importer recibe roster/subjects sin secretos IdP.
La siembra SQL es transaccional, auditada e idempotente para el mismo conjunto
intacto: no resetea bajas/versiones ni reasocia identidades desaparecidas a hijos.
No reprovisionar el roster para restaurar cuentas de un ensayo.

## Ensayo integrado y gate de CD

El CD lee `e1_enabled` del entorno y, al habilitarlo, exige los cuatro jobs de
`.github/workflows/e1-checks.yml`: browser, cloud, staging-apk y archive-drill.
Un fallo bloquea promoción. Un cambio a false debe ser explícito y revisado;
los probes técnicos no acreditan E1. CD y ensayo comparten serialización en sus
callers, sin otro lock en el workflow reutilizable.

Para repetir el ensayo en main con su CI de push actual aprobado:

```bash
gh workflow run e1-trial.yml --ref main -f ci_run_id=ID_CI_MAIN_APROBADO
```

Publica checksum/OCI digest verificados, abre RDS, migra con Migrate y despliega
API/archivo con Deploy. No admite CI de PR/forks ni candidatos anteriores a main.
El archivador usa el mismo digest aprobado y termina en tres horas; el relevo
verifica RUNNING/digest antes de detener el anterior. API rearma su retirada.

Browser usa E1Acceptance, Chromium/TOTP reales y el cliente móvil compartido.
Captura el callback custom-scheme en memoria mediante CDP Fetch antes de abortar
la navegación externa; conserva state/PKCE y validaciones del IdP. La regresión
local está en `tests/staging/native-callback.test.mjs`. No acredita retorno en
Android físico. Sin fixtures completos falla; trazas, screenshots y registro de
credenciales/códigos/tokens están deshabilitados.

Cloud usa E1Verifier y contrasta configuración efectiva, firmas, versiones,
retención y denegaciones no destructivas. El APK se genera desde checkout limpio
con `org.retiroseguro.staging`, scheme `retiro-seguro-staging` y endpoint del JSON.
Firma de desarrollo, manifiesto público y binario interno sin publicación en el
repositorio público. Los reportes parciales mantienen `e1_accepted=false`; el
conjunto aceptado y sus límites están solo en el plan.

### Baja y restauración

Browser usa una tarea privada importer sin taskRole ni credencial SQL en el
runner. Solo modifica `e1-a-p1` y `e1-b-guard`, conserva issuer/sub/rol/escuela/
sede/vínculos y audita mediante una función estrecha. Cada cambio es transaccional;
restore-all intenta ambas restauraciones en finally y en un paso always.

Con access recién renovado, la baja debe causar 401 antes de 240 segundos, rechazar
refresh y login con MFA válido. Restaurar no reactiva el access anterior: solo
un login nuevo permite entrar con el mismo alcance. Logout admite un refresh
retirado para revocar la familia; reutilizarlo para renovar registra replay y
revoca. El móvil bloquea uso local si falla el borrado de SecureStore, sin informar
falsamente que lo borró.

### Archivo ausente o tardío

Archive-drill pausa solo tareas `retiro-staging-archive` cuya definición, digest,
SHA y credenciales coinciden con el candidato. El login debe quedar DENIED y
conservar su contexto en memoria. Deploy reanuda la misma definición; el intento
previo sigue DENIED, un login nuevo protegido abre y el verificador externo cubre
la secuencia denegada archivada tardíamente. Reiniciar el proceso no prueba por
sí solo recuperación funcional.

El coordinador usa identidades Deploy/Acceptance/Verifier independientes, sin
recibir SQL/MFA/firma. Recupera en finally y en un paso adicional; guarda solo
señales/metadatos. No altera objetos, retención, claves o evidencia para provocar
el fallo.

## Copia SQL privada y recuperación independiente

Con migraciones aplicadas, esperar el final de los ensayos y suspender nuevas
consultas durante la captura. Desde CloudShell con el SDK operativo instalado:

```bash
PYTHONPATH=work/e1-sdk python3 -m scripts.prepare_e1_snapshot --synthetic-only
```

Una tarea privada importer, sin root/migrador/Django/firma, registra una lectura
técnica fija y exporta bytes canónicos. Cierra SQL antes de transportar por
CloudWatch privado. El operador recoge el stream sin imprimirlo y conserva en
S3 privado la copia original y otra reescrita con cadena local válida, ambas
COMPLIANCE siete días en acceptance-snapshots. No crea eventos o anclas falsos.
Límites: 5.000 filas/8 MiB canónicos y contenedor/reportes de 16 MiB.

La inspección privada contrasta seis roles SQL sin privilegios elevados,
escritor NOLOGIN, RLS ENABLE/FORCE, definers con search_path fijo, lector sin
menores y políticas efectivas IAM/KMS. Comprueba el roster original cerrado de
13 cuentas, dos escuelas/sedes, ocho padres, seis estudiantes y doce vínculos;
acepta incrementos legítimos de versión, pero rechaza filas extra o vínculos
cambiados. El informe retenido contiene booleanos, no secretos o filas SQL.

El comando devuelve solo report_key, report_version y report_sha256. Ejecutar
`e1-recovery.yml` en main con esos tres inputs y `external_minimum_sequence`,
el último high-water externo ya verificado. Su E1Verifier sin SQL/Sign/Put
comprueba versión/retención/hash; debe aceptar la original y rechazar
específicamente la divergencia de la reescrita. Una caída del archivo no demuestra
detección de alteraciones. Los reportes públicos solo contienen resultados y
high-water; las copias permanecen privadas.

Para comparar directamente una copia privada con la configuración del verificador:

```bash
PYTHONPATH=apps/backend python -m archive_worker.verify_cli \
  --minimum-sequence ULTIMO_HIGH_WATER_EXTERNO \
  --database-snapshot work/copia-privada.json
```

La copia es una lista de `sequence`, `event_id`, `canonical_base64` y `digest`,
máximo 16 MiB; debe cubrir exactamente el archivo anclado seleccionado. Confrontar
bytes/UUID/digest con versiones y manifiestos firmados, sin publicar la copia.
Este procedimiento no sustituye la recuperación integral del dominio prevista en E5.

### Recuperación Cognito y bloqueo nativo

Para incluir controles privados durante la captura:

```bash
PYTHONPATH=work/e1-sdk python3 -m scripts.prepare_e1_snapshot \
  --synthetic-only --exercise-cognito-controls
```

Solo cambia la contraseña de `e1-a-p1`, tras MFA reciente, conservando subject y
verificando contraseña nueva/MFA y rechazo de la anterior si difiere. Guarda
antes una contraseña pendiente en Secrets Manager para reanudar interrupciones;
si ya autentica, finaliza el checkpoint sin reasignarla. El cliente administrativo
temporal sin OAuth se elimina en finally; no se crean vínculos, invitaciones o avisos.

En `e1-b-s2` exige cinco fallos ordinarios, bloqueo explícito, vencimiento y sexto
fallo real. La segunda ventana debe superar estrictamente la cota superior de la
primera incorporando latencia RPC; finalmente exige vencimiento y MFA correcto.
Throttling, otros errores y esperas nominales no demuestran crecimiento. El
informe conserva las cotas; el diagnóstico solo muestra etiquetas constantes,
native_outcome y elapsed_ms, nunca respuestas o secretos del proveedor.

### Límite backend de RFS07

Es una política distinta del bloqueo nativo Cognito. `ci.yml` permite despacho
manual con `test_e1_limits=true`, `expected_release_sha`, `expected_image_digest`
y `expected_origin` del reporte de despliegue aprobado activo. El job public-limits no
recibe OIDC AWS ni secretos: hace cinco exchanges inválidos, comprueba bloqueo
de start y disponibilidad web, denegación a 890 s y recuperación a 905 s.
Mantener el mismo despliegue durante la prueba, sin adelantar reloj o modificar
filas. El reporte registra muestras, no una medición continua ni atestación del
SHA por la respuesta de la API.
