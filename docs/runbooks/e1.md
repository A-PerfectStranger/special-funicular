# E1 — identidad y evidencia sintéticas

E1 está en implementación. Este runbook describe comandos existentes y separa
preparación, pruebas locales y aceptación real. No habilita retiros ni datos reales.

## Desarrollo y comprobación

`make install db check` instala locks, actualiza roles locales de forma idempotente,
migra con identidad separada y ejecuta suites con PostgreSQL real. `make db` no
borra volúmenes. `infra/local/e1-roles.sql` es exclusivamente sintético local;
no aplicarlo en AWS. `.env.example` mantiene `E1_IDENTITY_ENABLED=false`.

Las pruebas usan identidades SQL reales runtime/importer/lector/archiver/notifier.
El propietario migrador solo se usa para DDL y para inyectar reloj/recibos operativos
en pruebas claramente simuladas. Los eventos no se limpian ni se reescriben.
Las suites OIDC usan firmas RSA reales, pero simulan al proveedor; las de archivo
simulan S3/KMS. Ninguna sustituye aceptación AWS.

## Comisión AWS con operador

Revisar el commit y `infra/aws/e1-staging.yaml` antes de ejecutar. El stack crea
Cognito con TOTP obligatorio, bucket privado Object Lock COMPLIANCE siete días,
claves KMS distintas y credenciales/roles separados. La retención sintética fue
autorizada por el usuario; no define retención productiva. Recursos de evidencia,
claves y secretos quedan retenidos. No destruirlos para ahorrar costes mientras
sean necesarios. El operador de cuenta sigue siendo una función administrativa
privada: jamás entregar sus permisos a la aplicación ni desproteger claves vigentes.

Cognito usa Essentials/Managed Login v2: la interfaz clásica no soporta
`prompt=login` y no cumple la reautenticación reciente requerida. El adaptador
comprueba pool, MFA, dominio v2 y cliente exactos antes de aceptar el token.
Documentación oficial: https://docs.aws.amazon.com/cognito/latest/developerguide/authorization-endpoint.html.
El presupuesto/preflight sigue siendo obligatorio; no ampliar el plan de cuenta
automáticamente si AWS rechaza el nivel seleccionado.

Desde un checkout limpio del commit revisado en CloudShell, autenticado en la
cuenta del proyecto y con AWS CLI/Python 3:

```bash
python3 -m scripts.commission_e1 \
  --web-origin https://re-ebedcb6688b94b228cd28424e44448c6.ecs.us-east-1.on.aws
```

Usar el origen observado del destino vigente; la URL temporal puede cambiar al
recrear Express. El comando comprueba cuenta, identidad de operador, presupuesto

No se crea otra BD, NAT ni ALB. El código no imprime saldos ni valores de secretos.

Un fallo se inspecciona privadamente en eventos CloudFormation/CloudWatch. No

## Procesos y permisos

- API/web: `retiro_runtime`; lector de accesos `retiro_system_read` con contraseña
  separada/DSN, sin SELECT sobre estudiantes o eventos completos. Django guarda
  la sesión en servidor; cookies HttpOnly/Secure/SameSite y CSRF.
- Archivo: `retiro_archiver`, `ARCHIVE_DATABASE_URL` o PGUSER/PGPASSWORD propios,
  APP_ENV=staging, AWS_REGION, ARCHIVE_BUCKET, ARCHIVE_KMS_KEY_ARN,
  MANIFEST_KMS_KEY_ARN y ARCHIVE_RETENTION_DAYS=7. Sin credenciales web/migrador.
- Verificador: identidad AWS independiente de lectura/Decrypt/Verify, sin Sign,
  PutObject, SQL ni acceso a credenciales de negocio.
- La confianza del verificador usa el OIDC existente de GitHub/main, sujeto
  inmutable y audiencia STS exactos; no depende del ARN de la sesión CloudShell.
  `scripts/aws_oidc.py --role E1Verifier -- ...` solo funciona desde main.
- Importación/migración: privadas; nunca inyectarlas en API o móvil. Bulk,
  activación y operaciones técnicas productivas siguen siendo E2.

Archivo cloud acotado:

```bash
python -m archive_worker.runner --max-runtime-seconds 10800
```

Diagnóstico Django con configuración de worker:

```bash
python manage.py runworker --archive --check
python manage.py runworker --archive --once
python manage.py verify_archive --minimum-sequence 1
```

El mínimo del verificador debe ser el último high-water mark externo confiable,
conservado por el operador fuera de la BD, no un valor obtenido de una BD que se
está investigando. Los checkpoints firmados referencian versión/hash exactos de
manifiestos y eventos. Una discrepancia suspende el acceso afectado y preserva
evidencia; no corregir hashes en la BD para hacer pasar la verificación.
El formato canónico versionado es `pg-jsonb-utf8-v1`; se protegen los bytes originales.
La firma KMS es RSA-3072 PSS SHA-256; no criptografía propia. La rotación de la clave
asimétrica y recuperación deben conservar claves/versiones previas y requieren
ensayo real; no están acreditadas por los tests de firmas locales.

## Comparación externa de una copia de BD

El verificador independiente funciona sin Django, SQL ni clave de sesión web:

```bash
python -m archive_worker.verify_cli --minimum-sequence ULTIMO_HIGH_WATER_EXTERNO \
  --database-snapshot work/copia-privada.json
```

El archivo privado es una lista de objetos con `sequence`, `event_id`,
`canonical_base64` y `digest`; tamaño máximo 16 MiB. Debe cubrir exactamente el
archivo anclado hasta el instante seleccionado. La comprobación confronta bytes,
UUID y digest de cada fila con versiones S3/manifiestos firmados, y detecta
borrados o una reescritura aunque se recalculen los hashes SQL. El archivo no se
publica ni se usa una BD investigada para elegir el high-water externo confiable.
El ensayo real de exportación/copia divergente sigue pendiente.

Logout puede revocar la familia mediante un refresh ya retirado por rotación.
Reutilizarlo para renovar revoca la familia y registra SESSION_REFRESH_REPLAY;
no recupera acceso. El móvil bloquea el uso local aun si el SO rechaza borrar
SecureStore, y no informa falsamente que el borrado se completó.

RFS07, decisión autorizada: Cognito conserva su bloqueo exponencial nativo
(tras cinco fallos empieza en un segundo y aumenta hasta aproximadamente quince
minutos); el backend aplica cinco fallos en quince minutos y bloquea quince
minutos en sus entradas. La pantalla del IdP no comparte el limitador del BFF.

## Despliegue acotado para aceptación

El CD habitual conserva `e1_enabled=false` en staging. Tras actualizar el stack y
migraciones del candidato, `E1 synthetic trial` se ejecuta en main con el ID de su
CI de push aprobado. Reutiliza la publicación con checksum/OCI digest verificados,
abre la ventana privada RDS, aplica migraciones con Migrate y despliega API/worker
con Deploy. No admite CI de PR/forks ni candidatos anteriores a main.

El archivador comparte exactamente la imagen aprobada, sin secretos Django/SQL
runtime/migrador, y termina como máximo en tres horas. El relevo contrasta digest
y estado RUNNING antes de detener los archivadores anteriores de esa familia;
un arranque fallido conserva el anterior. API mantiene su retirada programada.
El reporte distingue `e1_identity_enabled=true` de `e1_accepted=false`: los probes
técnicos no aceptan funcionalidad E1. Un CD ordinario posterior vuelve a la
configuración desactivada hasta cambiar explícitamente la configuración al cerrar
la aceptación. Producción y retiros permanecen bloqueados.

DescribeUserPoolDomain requiere `Resource: '*'` porque AWS no soporta recurso
individual para esa consulta; se limita a la región del stack. Las demás lecturas
Cognito siguen restringidas al pool. Fuente: https://docs.aws.amazon.com/service-authorization/latest/reference/list_cognito-idp.html.

El workflow de ensayo contiene además `browser` y `cloud`, con identidades
E1Acceptance/E1Verifier separadas. Browser lee solo fixtures de Secrets Manager,
usa Chromium real/TOTP y el cliente móvil compartido con captura del retorno
custom-scheme a nivel de protocolo; no acredita instalación/retorno Android nativo.
Sin fixtures completos falla de forma explícita. Las trazas/screenshots/valores
privados están deshabilitados. Cloud conserva un high-water externo, verifica
configuración real, firmas/versiones y denegaciones no destructivas. Los reportes
mantienen `e1_accepted=false`: recuperación con copia SQL y fallos/retardo todavía
requieren pruebas adicionales; un PASS de esos dos jobs no cierra todo E1.

El job staging-apk compila para `org.retiroseguro.staging`, scheme
`retiro-seguro-staging`, callback ya registrado y endpoint del JSON de staging.
Firma exclusivamente de desarrollo. Manifiesto SHA-256 público; APK interno no
se publica mientras el repo sea público. No proporciona distribución privada ni
prueba física (E5). Se genera desde checkout limpio con SHA exacto.

copia reescrita, aun con cadena local válida. Una caída del archivo no cuenta como

## Retorno nativo en el navegador de ensayo

Chromium puede omitir el evento response de una redirección a un esquema nativo.
El harness captura sus cabeceras mediante CDP Fetch antes de navegar al protocolo
externo; aborta esa navegación y entrega la URL solo en memoria al cliente móvil
compartido. Nunca imprime el código ni lo persiste. El cliente sigue verificando
callback/state/PKCE y el BFF verifica el IdP; no se altera la autenticación del
producto. Dos regresiones con Chromium real cubren captura y rechazo de un
esquema ajeno. Esto sigue sin acreditar retorno Android en un dispositivo físico.

La exportación privada incluye inspección de los grants reales: seis roles SQL
sin SUPERUSER/BYPASSRLS/DDL, sin escritura libre de eventos ni SET ROLE del escritor;
escritor NOLOGIN, RLS ENABLE/FORCE, lector de sistema sin tablas de menores y
search_path fijo en definers. El operador inspecciona además las políticas KMS
vigentes de denegación administrativa a roles de servicio y la política real del
rol API, sin acceso a secretos o firma. Solo se conservan booleanos en el informe
privado retenido. Esto es inspección del operador; la comparación del archivo se
realiza después con una identidad independiente sin SQL. Estas comprobaciones
nuevas aún no están acreditadas en AWS.
