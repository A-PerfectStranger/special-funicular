# Operación privada y ensayo E2

Contrato: RF01–RF06/RF14, RFS02/03/08/19/20, AT01/02/04 y AB18/20/24.
Estado y criterios de aceptación en PLAN.md. Los comandos de este documento están
implementados; su existencia no acredita una ejecución AWS. Usar datos sintéticos
hasta cerrar E5 y configurar las políticas institucionales.

## Importación y aprobación

`family_ops` es un comando técnico, sin endpoint administrativo. Usa exclusivamente
`IMPORT_DATABASE_URL` de `retiro_importer`; en cloud exige `sslmode=verify-full`.
Inyectar esa credencial desde la custodia privada, nunca escribirla en comandos,
Git, logs, APK o variables públicas. API, web y archivador no la reciben.

El JSON UTF-8 versión 1 tiene `schema_version`, `id`, `school_id`, `parents`,
`students`, `links`; no admite campos adicionales ni claves duplicadas. El esquema
implementado está en `school_roster/management/commands/family_ops.py`. Cada padre
incluye UUID estable y `contact` email en minúsculas; cada estudiante, UUID estable,
`site_id`, `name`, `blocked` y `windows`. Cada ventana tiene `weekday` ISO 1–7,
`from`/`until` HH:MM y `start_date`/`end_date` inclusivas. La escuela/sede deben estar
precargadas por el proceso técnico E1. Los enlaces incluyen `student_id`,
`parent_id`, `principal`; exactamente un principal por estudiante. Los UUID se comparan por su valor: distintas grafías del mismo UUID no pueden
representar dos padres. Son identificadores institucionales precargados, nunca datos que el padre introduce.

Límites por lote: 1000 estudiantes, 2000 padres, 4000 vínculos, 4 MB. Un padre
precargado puede recibir otro estudiante cuando UUID/contacto/escuela coinciden;
no se reasocia su identidad. Cambios incompatibles requieren revisar el lote,
no sobrescribir datos existentes. No ampliar automáticamente a otra escuela.

Con el archivo privado en `work/batch.json`, una identidad técnica y las variables
de Django cargadas conforme a README:

```bash
batch_id=$(python3 -c 'import json; print(json.load(open("work/batch.json"))["id"])')
batch_hash=$(sha256sum work/batch.json | cut -d ' ' -f 1)
uv run python apps/backend/manage.py family_ops stage --id "$batch_id" --sha256 "$batch_hash" --operator OPERADOR --file work/batch.json
```

La escuela revisa el lote exacto y conserva su aprobación fuera del repositorio,
ligada al SHA-256. El equipo técnico registra su referencia, sin inventarla:

```bash
uv run python apps/backend/manage.py family_ops approve --id "$batch_id" --sha256 "$batch_hash" --operator OPERADOR --approval REFERENCIA_ESCOLAR
uv run python apps/backend/manage.py family_ops promote --id "$batch_id" --sha256 "$batch_hash" --operator OPERADOR
```

Staging no activa filas. Promoción revalida, bloquea la escuela y los UUID de padres en orden global,
comprueba contacto/escuela bajo lock y crea el lote en
una transacción con evento/outbox; un error revierte todo. ID/hash idénticos son
idempotentes; mismo ID con bytes distintos falla. La aprobación se vincula al
hash de los bytes almacenados, no al nombre del archivo. Una familia pertenece
a una sola escuela, incluso entre promociones concurrentes. Comprobar protección posterior con el archivador
y el verificador E1: un commit SQL no se anuncia como recibo WORM.

## Invitación y alta familiar

```bash
uv run python apps/backend/manage.py family_ops invite --id UUID_PADRE --operator OPERADOR --approval REFERENCIA_ESCOLAR --output work/invitation.private
```

El comando crea un archivo nuevo modo 0600, sin mostrar el token; en BD solo queda
SHA-256, emisión/caducidad de 24 h, uso y revocación. La entrega al contacto
precargado y verificado corresponde al canal operativo privado, fuera de logs y
URLs. Este comando no envía email/SMS. Una nueva emisión revoca invitaciones
pendientes; no permite reasociar un padre activado. Revocar una invitación mediante
la operación técnica específica, sin borrar su historia.

En móvil: activar con invitación → navegador OIDC/PKCE S256/MFA → canje que compara
`email_verified=true` y `email` del ID token firmado con la precarga exacta
(sin plegar mayúsculas de un buzón distinto) → ingreso
normal. Ningún `email`, documento, rol, hijo o principal declarado en el cuerpo
acredita un vínculo. El canje no devuelve datos familiares ni tokens OIDC.
Solo `issuer`/`sub` quedan asociados; recuperación E1 conserva esos identificadores.

## Personal, principal y restricciones

`family_ops technical --id UUID_COMANDO --operator OPERADOR --approval REFERENCIA_ESCOLAR --file work/technical.json`
recibe JSON con `operation`, `school_id`, `target`, `data`, `reason`. No admite SQL.

| Operación | Target / data |
| --- | --- |
| `PROVISION` | UUID cuenta nueva; `role` GUARDIA/ADMIN_ESCUELA/ADMIN_SISTEMA, `issuer`, `subject`, `site_id` (null salvo guardia). Escuela null solo para ADMIN_SISTEMA. Identidad IdP individual/MFA ya comprobada por el operador. |
| `DEACTIVATE` | UUID cuenta; `data: {}`. Corta sesiones online y autorizaciones familiares afectadas; no elimina hechos. La baja de un PADRE es global a su cuenta, incluso si tiene varios estudiantes. |
| `CHANGE_PRINCIPAL` | UUID estudiante de la escuela; `data: {"parent_id":"UUID_VINCULO_ACTIVO"}`. |
| `SET_POLICY` | UUID estudiante; `data` con `windows` completas y `blocked` booleano. No existe ampliación de horarios desde las apps. |
| `REVOKE_INVITATION` | UUID invitación de la escuela; `data: {}`. |

Motivo, aprobación, ejecutor y credencial quedan auditados, sin documentos ni
secretos completos. Replay del mismo comando conserva resultado; contenido distinto
falla. Principal y restricciones bloquean primero el estudiante, invalidan versiones
/autorizaciones y sesiones pertinentes en la misma transacción. El orden de E3 debe
adquirir ese mismo bloqueo antes de emitir/confirmar y revalidar versiones; todavía
no hay QR ni permiso de entrega física que se pueda probar en E2.

## Autorización familiar

Las rutas figuran en OpenAPI. PADRE vinculado consulta; solo el principal modifica.
Cambios exigen MFA de antigüedad <=5 min, validada dentro del comando SQL. El móvil
expone reautenticación; ante rechazo pide reingresar y consultar el estado.
Cuidadores requieren nombre/documento/foto completa. La foto JPEG/PNG se decodifica
con límites, se reencodifica RGB JPEG sin metadata (máximo 640 px) y se sirve solo
con sesión/vínculo vigente y `no-store`. La limpieza móvil elimina solo copias
temporales bajo la caché propia, nunca el original seleccionado en galería.
No se guarda copia de la cédula.

Autorización por una fecha: inicio=fin y el día ISO correspondiente. Recurrencia:
fechas inclusivas finitas y días ISO, máximo 366 días/ocurrencias. El servidor usa
la zona IANA de la sede y rechaza horas locales inexistentes/ambiguas, pasado,
intervalos vacíos, cruce de medianoche o salida de la ventana escolar. Guarda las
ocurrencias UTC; no crea QR permanente. Actualizar cuidador revoca autorizaciones
previas; revocar es un comando nuevo. Los POST requieren UUID `Idempotency-Key`
ligado al actor/cuerpo; tras respuesta perdida conservar ambos y consultar/reintentar.
`event_sequence` permite verificar el resultado contra el archivo externo.

## CloudShell: preparación revisable del ensayo sintético

Primero integrar un candidato con CI completo y E2 apagada. No ejecutar estas
instrucciones desde un SHA distinto del que se va a ensayar. La sesión CloudShell
debe ser de operador de la cuenta del proyecto; CI/runtime no sustituyen esa
identidad. No proporcionar códigos de verificación, contraseñas o TOTP al chat.

Usar un directorio nuevo evita ejecutar Git desde `~` o modificar un checkout
previo. Sustituir `SHA_MAIN_APROBADO` por los 40 caracteres del candidato con CI
completo. Revisar los scripts antes de ejecutarlos:

```bash
(
  set -euo pipefail
  e2_checkout=$(mktemp -d /tmp/retiro-e2.XXXXXX)
  git clone https://github.com/A-PerfectStranger/special-funicular.git "$e2_checkout"
  cd "$e2_checkout"
  git switch --detach SHA_MAIN_APROBADO
  python3 -m pip install --target work/e1-sdk --require-hashes -r infra/aws/e1-ops.txt
  export PYTHONPATH="$PWD/work/e1-sdk"
  trial_id=$(python3 -c 'import uuid; print(uuid.uuid4())')
  python3 -m scripts.provision_e2_fixtures --sha "$(git rev-parse HEAD)" --trial-id "$trial_id" --pool-size 4 --synthetic-only
)
```

Si los clientes todavía no permiten `email`, ejecutar antes, en ese checkout:

```bash
staging_origin=$(python3 -c 'import json; print(json.load(open("infra/environments/staging.json"))["base_url"])')
python3 -m scripts.commission_e1 --web-origin "$staging_origin"
```

Revisar primero el diff de `infra/aws/e1-staging.yaml`: el cambio necesario para
activación añade `email` a los scopes autorizados; no cambia IAM, retención ni
claves. La comisión existente hace preflight de cuenta/presupuesto y abre una
ventana acotada. No cambiar de plan ni enviar mensajes reales ante un bloqueo.
Cada cohorte crea dos identidades nuevas con contactos `@synthetic.invalid`,
mensajería suprimida y TOTP. Contraseñas/semillas/invitaciones quedan exclusivamente
en Secrets Manager. Conserva las trece identidades E1; no reasigna subjects.
La prueba marca el contacto sintético verificado por operador; no acredita un
canal productivo de verificación o envío de invitaciones.

`--pool-size 4` prepara cuatro cohortes independientes (ocho cuentas); el límite
es ocho cohortes por catálogo. Omitirlo conserva el ensayo único ligado al SHA.
Un pool preparado puede ensayar releases posteriores: cada ejecución se liga al
SHA/digest desplegado y reserva una cohorte mediante promoción privada atómica.
Solo se salta una cohorte que ya tiene filas durables; errores de infraestructura
o validación bloquean el gate. CI no crea cuentas Cognito ni escribe el vault.

Al agotarse, el gate falla con `E2_COHORT_POOL_EXHAUSTED`. Preparar otro pool con
`trial_id` nuevo; los registros SQL, subjects y canjes anteriores se conservan.
Secrets Manager retiene versiones anteriores del catálogo. Reponer también si
las ventanas finitas ya no cubren el ensayo. Para reanudar una preparación
interrumpida, conservar SHA, trial_id y tamaño originales. No reutilizar una
cohorte consumida ni cambiar datos para simular un ensayo nuevo. Una interrupción de enrolamiento
que no pueda reanudarse con seguridad queda bloqueada para inspección privada;
no reemplazar semillas, subjects o sesiones para aparentar éxito.

Con el CI main aprobado, ejecutar workflow **E2 synthetic trial** (`e2-trial.yml`)
con su `ci_run_id`. Publica el OCI aprobado, migra con identidad separada y habilita
E2 solo en el ensayo sintético acotado. Mantiene el grupo serializado de CD y el
mismo digest API/archivador. Primero exige el gate E1 completo/APK; después carga
lote privado, rechaza doble principal y enfrenta dos escuelas concurrentes por
la misma familia (exactamente una promueve). Canjea invitaciones con Cognito real,
rechaza replay y comprueba permisos, idempotencia, cuidador/revocación, recurrencia
semanal, horarios, cambio de principal, restricciones y baja online.
Finalmente E1Verifier comprueba WORM/KMS/manifiestos hasta la secuencia de la última
mutación E2. No hay nueva política IAM ni credencial importer en el navegador.

Los reportes de Actions llevan SHA, trial y alcance; `e2_accepted=false` es
intencional: hay que contrastarlos con todos los criterios de PLAN.md, incluidas
las pruebas SQL/contrato/imagen/APK. No acredita teléfono físico ni E3/E5. Un
callback/origen recreado, fixtures ausentes o cualquier job fallido bloquea la
aceptación. No se omiten esos errores ni se heredan pruebas de otro commit.
`e2-checks.yml` concentra el mismo gate para ensayo y CD habitual. La bandera
`e2_enabled` en staging sigue en false hasta aceptar el candidato con pool real.
Al habilitarla, CD exige E1, luego E2 y WORM independiente antes de considerar
producción, cuyo destino sigue bloqueado por E5. Todos los caminos serializan
con CD; no integrar otro main mientras archive-drill requiera su guard de latest main.
Un pool agotado bloquea la promoción y requiere reposición de datos de ensayo,
sin aprobación manual rutinaria ni permisos de provisioning para CI.
